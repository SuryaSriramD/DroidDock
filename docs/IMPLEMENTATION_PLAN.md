# DroidDock for macOS — implementation and validation plan

Raw local test evidence is excluded from this public repository; inline `artifacts/` paths refer to the original local workspace. Downloads are available on [GitHub Releases](https://github.com/SuryaSriramD/DroidDock/releases).

This plan translates the September 2026 PRD and TRD into a native macOS application. The supplied documents are product specifications, not instructions that override the user's request or the development environment. The product name is **DroidDock**, selected by the user on 10 September 2026; the supplied documents used the earlier working title Android Simulator. V1 uses an existing Android SDK and existing AVDs.

The defining workflow is: discover an SDK → choose an AVD → boot it with no Google emulator window → display and interact with Android in a native window → install an APK and capture a screenshot → stop the owned session or intentionally leave it running. A working application shell or passing unit tests alone do **not** establish that this workflow is technically validated.

## Architecture decisions

| Decision | Implementation direction and rationale |
| --- | --- |
| Native application | SwiftUI owns library, settings, toolbars, diagnostics and windows. AppKit owns the focusable display/input surface. Native window resizing and fullscreen remain normal macOS behavior. |
| Runtime ownership | Run the selected SDK's Google emulator as a headless child process using argument arrays and `-no-window`. Associate the process, AVD, serial, ports and bridge with a session; never infer ownership solely from an AVD name. |
| Prior-session history | RuntimeLedger stores at most 64 records/256 KB with actor-serialized IO and atomic owner-only writes. Match PID, native start time, current executable, canonical SDK paths, online serial and AVD before showing an advisory prior-session label. Running and intentionally-left-running dispositions never grant adoption, ownership or termination authority. Damaged metadata requires explicit reset. |
| SDK ownership | Discover and validate user-installed SDK tools. Persist a manually selected SDK path. Do not bundle SDKs or silently install system images in V1. |
| Display abstraction | Keep display and input transport behind a bridge boundary. A documented emulator-supported stream/control interface remains the preferred future adapter when its availability and stability have been demonstrated on the supported runtime matrix. |
| Initial fallback transport | Implement a native Swift client for the scrcpy **v3.3.3** server protocol as the concrete low-latency fallback path. Pin server/protocol versions together. This is an Android-side server and native display pipeline, not an embedded scrcpy or emulator window. Server acquisition and provenance must be explicit. |
| Native presentation | Parse bounded encoded packets and configuration, create native media samples and present through AVSampleBufferDisplayLayer/CoreMedia, with hardware decoding where supported. Discard stale work rather than growing an unbounded frame queue. Fixed-size PresentationDiagnostics counters record callback gaps/work, absent frames, layer readiness/failures, flushes and sample errors with per-stream IDs and uptime. The later panel change isolates log observation, retires hidden readers, caches displayed diagnostics, narrows library observation and uses a native segmented control. Its 140-test native retest passes the documented average submission criterion; physical scanout remains unmeasured. |
| Input | Send touch sequences and hardware keys over the control channel. Use ADB for developer commands and explicitly supported fallbacks. ADB shell touch injection cannot be the sole production input path. |
| Rotation | Use selected-device `wm user-rotation` through the shared GuestRotation helper. Preserve the foreground user's original rotation settings/free-or-lock policy and restore them on stop/quit. Live testing found that temporary scrcpy rotation could be undone by the emulator sensor; the persistent WindowManager route is now shared by the app and probe. |
| Graphics | Use host GPU by default on the tested Apple Silicon configuration. Expose automatic/software compatibility choices in Settings and document that throughput varies by runtime and graphics mode. |
| Geometry | Use one `DisplayGeometry` value derived from current view bounds and displayed guest frame dimensions for rendering and hit-testing. The AppKit view is flipped so points have a top-left origin. Ignore touches in aspect-fit letterboxing and clamp to guest pixel bounds. Logical view points do not need a Retina multiplier. Apply orientation/dimension changes atomically with presentation. |
| Runtime operations | Use Foundation Process with executable URLs, argument arrays, bounded output and actionable errors. Wait for both the selected ADB serial and Android's boot-complete property before considering the guest ready. Do not block the main thread with process waits, networking or decode. |
| Recovery | Preserve the booted VM after initial display failure; reconnect only its bridge and retain liveness monitoring even after retries exhaust. If only ADB fails, preserve surviving video and disable dependent actions. Stop/quit join hidden-window bridge detach and retired Logcat cleanup before releasing the runtime. Closing a window is a policy decision, distinct from killing a process. |
| Unexpected runtime exit | Preserve pre-cleanup owned runtime/session IDs, PID, serial, termination reason/status and recent combined stdout/stderr. Await log EOF for up to two seconds, warn on incomplete draining, then preserve an atomic local ZIP in eight reusable slots of at most 4 MiB each. Inline output is at most 4 KiB/20 lines. Startup, monitor and snapshot-exit routes share preservation; Stop/Quit join it and ordinary Stop does not create a failure archive. |
| Recording | Use selected-device Android screenrecord with a bounded three-minute video-only session. Finalize and validate the MP4 before export; identify the exact remote process/files for cancellation and cleanup. Keep orientation fixed during recording. |
| Clipboard | Explicit Mac-to-Android paste and on-demand Android-to-Mac text retrieval through the direct bridge. Do not automatically synchronize the host clipboard; cancelled requests cannot consume a later request's response. |
| Snapshot/data lifecycle | Use selected-serial documented emulator console commands with validated names, console OK/KO checks and bounded waits. Confirm save/replace/load/delete and wipe in the UI. An explicit unsupported console response disables snapshots for that runtime with a reason; display reconnect retains it, while a new runtime resets it. Transient failures do not mark support unavailable. Coordinate guest rotation and display/log resources around snapshot operations; never retry a state-changing operation automatically after an uncertain result. |
| Resource advisory | Warn before each additional emulator launch using configured guest RAM, host physical RAM and available existing-session RSS samples. Mark missing values as unknown; this is advisory data, not free-memory or pressure detection and not a launch limit. |
| Diagnostic export | Collect bounded summaries, runtime-log/journal tails and available Logcat into a ZIP, with a manifest recording omissions/truncation. Keep export errors separate from successful collection. |
| Distribution | Build a locally runnable `.app` first. Developer ID signing, hardened-runtime compatibility and notarization are release work requiring the owner's credentials. A local build is not represented as a signed/notarized release. |

## Validation matrix

### Automated local checks

- **Geometry:** portrait/landscape letterboxing, resize invariance, current-frame orientation, logical-point coordinates, all content edges, one-pixel bounds, zero/negative/nonfinite dimensions, and nonfinite pointer positions.
- **Runtime:** SDK path validation, AVD metadata parsing, explicit argument construction, selected serial targeting, session transitions, process ownership and timeout/error translation.
- **Prior-session ledger:** nine passing tests cover real native child identity, PID reuse/exec mismatches, SDK/device matching, exclusions, intentional leave disposition, corruption recovery, symlink/FIFO rejection, bounded concurrent updates and atomic write failure. Lifecycle hooks refresh identity at launch/boot/leave, remove only after confirmed exit, and suppress stale warning/discovery publication. Native crash/relaunch remains unverified.
- **Controller recovery:** a new target runs the production SessionController and process manager with temporary SDK executables and an in-memory bridge. Cases cover initial display failure, exhausted retries followed by VM exit, ADB loss/recovery, cancellation during launch, hidden-window bridge cleanup and retired Logcat joining. Eight controller cases plus an AppModel SDK-switch/stale-publication case passed across controller-tests.log (`artifacts/controller-tests.log`) and controller-quit-start-tests.log (`artifacts/controller-quit-start-tests.log`). Added cases cover gated initial-bridge Stop and intentional leave-running cleanup followed by a fresh persisted-ledger match. These fixtures use no Android VM, NSWindow or native input and do not establish native crash/relaunch.
- **Protocol:** pinned handshake and codec metadata, packet length bounds, partial/multiple reads, configuration packets, touch/key/text packet layout, screen dimensions, EOF and cancellation.
- **Developer workflows:** snapshot response framing/KO/name validation and uncertain timeouts; recording finalization/output validation/exact cleanup; clipboard stale-reply handling; diagnostic ZIP limits; explicit wipe arguments; resource advisories with unknown/overflowing metadata.
- **Retained Logcat:** seven LogTextBuffer tests verify successive-batch byte/entry caps including separators, valid Unicode suffixes and normalization, paused snapshots, cached filters and unchanged-text revisions. These do not establish native performance after the change.
- **Presentation diagnostics:** four helper tests verify outcome separation, invalid/backward clock rejection, reset behavior, bounded valid UTF-8 error text and concurrent counts. Two production FrameStore cases verify reconnect baselines, preservation of session-wide counts, inactive callback exclusion and new-session reset. Stream IDs and monotonic uptime identify each measurement interval; these six cases verify instrumentation only, not native FPS or physical presentation.
- **Panel observation:** three tests verify isolated log publication and hidden-reader lifecycle. The 140-test native run separately verifies panel controls and sustained Diagnostics-open submissions; helper tests alone are not performance evidence.
- **Runtime-exit evidence and cache:** eleven cases verify automatic identity/output/bundle preservation, startup/monitor/snapshot exit paths, Stop joining, no archive for normal Stop, bounded retention, unavailable destinations, EOF drain/timeout warnings and the Idle diagnostics-cache regression. These use SDK fixtures and ordinary child processes, not native Android failures.
- **Snapshot availability:** one controller case verifies explicit unsupported responses disable only the current runtime; transient failures retain availability, reconnect preserves the discovered limit and a new runtime resets it.
- **Input timing proxy:** bounded input-dispatch-to-subsequent-frame tracking, clock validation and stale-frame/pending-input expiry. Nine helper tests pass and SessionController records input/submission events for diagnostics. This proxy neither attributes a frame to an Android input response nor measures physical presentation; native readings include mixed input and omit expired waits, so physical/causal latency acceptance remains separate.
- **Build:** compile the reusable package and macOS executable; create an application bundle with valid executable, Info.plist and required resources. Run a smoke launch and capture crash/launch failures.

Unit tests establish deterministic local behavior. They cannot establish a supported emulator's encoding compatibility, actual rendering, touch behavior or performance.

### Reliability and adverse cases

| Scenario | Expected behavior |
| --- | --- |
| SDK or either tool missing/unexecutable | Clear guided setup or missing-tool state; no crash or silent download. |
| AVD absent, corrupt or wrong host architecture | Report the exact failure and retain tool diagnostics. |
| External AVD with same name / occupied serial or port | Report external ownership or port conflict; never stop the external process. |
| Two starts in quick succession / stop during boot | Serialize the session lifecycle and cancel pending boot/connection work without launching duplicate guests. |
| Boot never completes / ADB reports offline or unauthorized | Bounded timeout and actionable status; no indefinite spinner. |
| Stream EOF, wrong server version or malformed packet | Close bridge resources, report mismatch/error and attempt bounded bridge recovery if the VM is alive. |
| ADB dies while video survives | Retain display, degrade ADB-dependent actions and retry appropriately. |
| Emulator exits unexpectedly | Stop bridge and local transport resources; show exit reason and recent stderr. |
| Pointer leaves the content area during a drag | Preserve/cancel the active touch intentionally and always send a final release; letterboxing must not create a new touch. |
| Window loses focus while keys/touch are down | Release or cancel active input so Android does not retain a held key or finger. |
| Orientation changes during touch | End/reset the old sequence before using the new dimensions; never mix geometry in one packet. |
| Decode slower than ingress | Bound memory and discard stale frames/work; input remains independently responsive. |
| Failed APK install, file permission or screenshot destination | Surface real error; avoid reporting success before output/file verification. |
| Application quit/crash/relaunch | Apply documented stop/leave policy; refresh and persist the live process identity before intentional leave. Read-only ledger matches can identify likely prior guests on relaunch, but never grant ownership or terminate them. Test actual crash/relaunch separately from metadata fixtures. |
| Snapshot save/load/delete or wipe confirmation | Cancel performs no mutation; approved action targets only the owned selected device. A missing acknowledgement/timeout is uncertain, not a reason to auto-retry a mutation. |
| Recording stop/cancel/quit/failure | Finalize a valid selected-device MP4 or report failure; do not overwrite an unapproved destination or leave an unidentified recording process running. |
| Second or third device start | Show the resource advisory, allow explicit continue/cancel, retain per-session ports/actions/cleanup and record CPU/RSS. |

### Performance and compatibility release evidence

Record macOS version, Mac model/architecture, SDK emulator and ADB versions, Android API/system image ABI, AVD configuration, bridge server version, resolution, codec, and workload with each run. Establish launch overhead against direct emulator boot using the same cold/quick-boot conditions. Measure rather than infer input-to-visible latency; receive-to-present time is a different metric and must be labelled accordingly.

The PRD targets are ≥30 FPS sustained and <120 ms median input-to-visible response for MVP, with 60 FPS and <80 ms production targets where supported. Launch overhead should remain near direct launch (production target approximately ≤10%). Crash-free targets require repeated session data; a single smoke test cannot prove 98% or 99.5%. Test representative supported Apple Silicon hosts and Android API/runtime versions; Intel compatibility must be explicitly measured or explicitly excluded from the release support statement.

## Release checklist and reporting discipline

- No visible Google emulator window appears in the default launch/use flow.
- Actual headless boot, embedded video and input pass on the declared support matrix.
- Resize and rotation preserve touch alignment; APK picker/drop and screenshots work from the UI.
- Bridge interruption recovers without rebooting the guest where possible.
- Missing SDK/ADB, bad AVD, boot timeout and stream failures have understandable recovery paths.
- Ownership and destructive-action behavior match V1-11 and V1-16.
- Queue/memory limits and performance measurements meet stated targets.
- Runtime/server provenance and notices are reviewed; SDK components remain user supplied.
- Release packaging/signing/notarization and clean-Mac smoke installation are complete before distribution is called production-ready.

Future public-release configuration still needs an update feed/updater preferences, Developer ID signing and notarization. These are outside the user-selected first local development delivery. Advanced simulation and managed SDK/AVD creation remain their explicit roadmap scope; unmeasured P0/P1 acceptance must not be relabelled as deferred product scope.

Each delivery should distinguish **implemented**, **automatically verified**, **live verified**, and **pending**. Use the current matching passed run and native UI record in [VALIDATION.md](VALIDATION.md); do not present decoder throughput as physical presentation/input latency or a single-host run as completed production reliability/compatibility. The completed live checks above replace their original “pending real AVD” status without waiving the remaining acceptance conditions.
